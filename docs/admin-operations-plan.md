# 利用者・課金・利用状況の管理

## 画面

- `/admin/users`：表示名・メール・UIDで検索できる25件ずつの一覧。Plus利用権／人物パックの絞り込み、登録日、最終練習、開始・完了・返信数を表示する。利用者の詳細は同じ画面内で開き、個人のUIDやメールをページURLへ含めない。
- 利用者詳細：登録情報、現在の契約・購入権・利用枠と期限、練習集計、6人の進行・好感度、直近20会話の日時・場面・往復数・評価状態を表示する。会話本文・設定全文・認証情報は返さない。
- `/admin/billing`：現在の有効Plus・人物パック購入者、期間・商品で絞れる購入枠の付与／停止／期限終了履歴、直近の契約とCheckout準備状態を表示する。支払額・返金額は保存されていないため未記録と明示し、商品価格から売上を推定しない。Checkout完了と支払確認済みの枠付与を区別する。
- `/admin/usage`：7・30・90日の登録、実際に返信した利用者、開始・完了・返信・枠消費・クリア・評価待ちを表示する。日別グラフ、人物別・3/6往復別の利用、利用者上位と、保持中の未ログイン体験を確認できる。
- 管理トップと管理ヘッダーに上記3画面への導線を追加する。既存の評価方針・人物設定は維持する。

## データと集計

既存テーブルから読み取り、migration・新しい依存関係・Stripeへの照会を追加しない。残枠は書き込みを行わない既存 `readCreditState` と同じ計算を使う。好感度・クリア状態は保存済みの集計を読み取り、管理画面の閲覧で再採点・精算・付与・消費を起こさない。

期間は日本時間の当日を含む7/30/90日、終端は集計時刻未満。日別の開始は `charged_at`、完了は `completed_at`、返信は保存済み `practice_turns.created_at` に計上する。画面を開いただけの下書きを開始件数に含めない。総合点と配慮の合格基準を満たすステージクリアは会話完了と別に集計する。好感度は次話の解放条件であり、クリア件数へ混ぜない。

登録利用者・返信した利用者・未ログイン体験は別の数値とし、訪問者数とは呼ばない。未ログイン体験は30日の保持・削除があるため保存分と表示し、ログインへの引き継ぎ分と合算しない。旧Dify形式の操作は利用者詳細で別項目にする。期間を変えても現在の契約人数は現在値のままであることを表示する。

一覧はDB側の検索・集計・ページ分割を使う。利用者詳細や課金履歴は必要な列と件数だけを選び、会話本文、Checkout URL、Stripe認証情報、未公開の人物／評価設定をブラウザへ返さない。

## 認可・通信

すべての新しいGET APIで `requireKnowledgeAdmin` を実行する。既存の検証済みGoogleアカウント／UIDの管理者判定を使い、保存プロフィールや本文の自己申告を権限にしない。各応答は `Cache-Control: no-store`。一般利用者は403、未認証は401。検索・期間・ページ番号を検証する。

画面では読み込み中・失敗・0件を区別し、エラーを0件の正常表示へ変換しない。検索・期間切替の古い応答や、ログアウト／アカウント切替前の応答を表示しない。管理画面のページビューは利用者向けの計測から除く。

## 検証・公開

PGliteで既存migrationを適用し、権限、検索・絞り込み・ページ分割、同時に複数の購入／枠／返信がある場合の重複防止、JSTの日付境界、期間の異なる開始／完了、管理者0枠消費、ゲストと引き継ぎ、失効・期限終了・予約中の枠を検証する。閲覧前後で各台帳が変わらず、会話本文や秘密のURLを返さないことを確認する。

PC・スマホを架空データで確認し、全テスト・型・lint・ビルドを実行する。PRレビュー後に本番へ反映し、公開コミットと未認証／一般利用者の拒否を確認する。本番課金の `BILLING_ENABLED=false` とProductionでの決済拒否は変更しない。

### ローカルでの確認結果

- 回帰テスト365件成功。型チェックはエラー・警告なし、ESLint・Prettier成功。
- Firebase Auth Emulatorと専用PostgreSQLの架空データで、PC 1280px・スマホ390pxの一覧／詳細／課金／利用状況を確認。検索、ページ送り、期間・商品切替、ログアウト時の情報消去、一般利用者の拒否を検証した。
- 本番ビルド成功。公開13ページ・サイトマップ・404と、新管理画面のnoindex／SSRの個人情報非出力、4つのAPIの未認証401を確認した。
- ローカルのファイル配置では既存のVercel成果物チェックの固定パスが一致しないため、実際の `.vc-config.json` のハンドラーからmanifestを読み、404用layout/errorの存在を確認した。Git経由のCIでは標準コマンドも実行する。
- 実際の支払額・返金額は既存DBにないため、本機能でも金額は表示しない。本番販売の開始や決済設定の変更は含めない。

### レビュー対応

`claimed_uid` は引き継ぎを再開できる本人の予約であり、成功記録ではない。引き継ぎ済みの件数は、同じ会話ID・本人の通常練習が存在し、保存済みの全ゲスト返答のrequest ID・位置が通常の返答台帳に揃った場合だけ数える。枠不足、下書きだけの作成、部分保存は成功へ含めない。未発言の体験は、本人の下書きの作成が成功した時点で引き継ぎ済みとし、練習開始とは区別する。

予約のみ／下書き／部分保存／全保存、別利用者、未発言の3つの回帰テストを追加し、関連22テスト・型・lintが成功した。架空データの実際のPostgreSQLとPC・スマホの画面でも、予約分が成功に含まれないことを確認した。
