# 決済レビュー対応

## 対象

PR #21の未解決2件を修正する。本番販売は有効化せず、本番DB・本番アプリ・Stripe設定を変更しない。価格・付与枠・UIの操作は維持する。

## 方針

1. Checkout作成の全パラメーターを、Stripeへの送信前に既存の購入予約へ保存する。同じ購入IDの再試行では、有効期限・価格・戻り先を含めて保存値を再利用する。作成処理の90秒の占有期限とは分離し、失敗時も保存値を消さない。期限切れの購入IDは新しい購入として扱わず、再読み込みを案内する。既存方式の保存値がない失敗予約も、同じStripeキーで再作成しない。

   初回のStripe有効期限は60分とし、送信前の保存処理に使う時間と、Stripeの最短30分に余裕を持たせる。ルート購入の価格照合も保存済みの元の価格IDを使い、復帰後の権利付与まで同じ購入内容で完了できるようにする。

2. 返金・紛争の状態をPaymentIntent単位で保存する。権利付与前に失効通知が来た場合も失効状態を残し、後続の購入完了・再照合では購入権と枠へ反映する。全額返金は紛争の勝訴でも復活させない。Plusの請求書にも同じ支払い状態を適用し、失効後の通知で枠を復活させない。
3. ユーザー行のロックと既存トランザクションを使い、通知処理と権利付与を直列化する。失効状態の記録とイベント処理済みの記録を同じトランザクションに含める。
4. schemaを正としてnullableのCheckoutパラメーター列と支払い状態テーブルを生成する。独立した検証DBにmigrationを適用し、再generateで差分なしを確認する。

## 検証計画

- Stripe側で作成済みなのに応答が失われた場合と、作成後のDB更新が失敗した場合を再現する。時間や設定が変わっても、同じキー・同じパラメーターで元の購入画面へ復帰し、セッションが増えないことを確認する。
- 全額返金・紛争が権利付与より先に届いた場合、後続通知と再照合で購入権・利用枠が有効にならないことを確認する。勝訴と全額返金の組み合わせ、Plusの返金先行も確認する。
- 既存の購入・重複通知・本人制限・枠消費の統合テスト、型・lint・ビルドを通す。今回の変更はサーバーと永続化のみで、画面変更はない。
- 修正をpushしてCI結果を確認後、対応するレビューの2スレッドを解決済みにし、再取得して状態を確認する。

## 検証結果（2026-11-08）

- 全186件の統合テスト成功。11件を追加し、通信応答の喪失、Stripe作成後のDB保存失敗、期限切れ・旧方式の予約、返金/紛争の先行、勝訴と返金の組み合わせ、Plusの返金の前後、一部返金を検証した。再試行では時刻・設定が変わっても同じリクエストを送り、セッションを増やさず、元の価格で購入権と24枠を付与できることまで確認した。
- `0005_reflective_amazoness.sql` はnullableの `billing_checkouts.request_params` と `billing_payment_states` の追加のみ。既存の列の削除・型変更はない。専用PostgreSQL（ローカル55441番）に全6件のmigrationを適用し、型・null許可を照合。再generateで `No schema changes, nothing to migrate` を確認した。本番や他の検証DBには適用していない。
- 型チェック0エラー・0警告、Prettier/ESLint・ビルド・Vercel出力検査が成功。
- 既存のStripeサンドボックスを読み取り、実際の支払い済み980円の請求書に対して、Invoice Paymentsの請求書指定・paid絞り込み・PaymentIntent参照の形式を確認した。今回追加の購入・返金・契約変更はしていない。通知の順序逆転・通信断は独立DBとSDK代替による統合テストで再現したもの。
- 今回はサーバー・DB・テスト・記録の変更のみで、新しい画面変更とキャプチャはない。CIとPreviewの最終状態はPR上で確認する。
